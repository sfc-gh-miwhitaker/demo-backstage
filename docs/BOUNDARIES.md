# Demo-Only Versus Production Boundaries

What this demo actually proves, what it only illustrates, and what production
integration still requires. Written so nobody has to guess in the room.

## The headline distinction

**Enforced in the data path, and therefore real:**

- Row access policies on both fact tables and on the label and track dimensions.
- Entitlements modeled as principal plus permission plus allowed label, so a
  principal can hold revenue access to a label without holding streaming access
  to it.
- No admin bypass. `SYSADMIN` sees everything because it holds entitlement rows,
  not because the policy exempts it.
- The semantic views and the agent sit above enforcement and cannot widen it. Two
  principals querying the same semantic view get different answers.
- `ENTITLEMENT` is not readable by any persona, so a subject cannot inspect or
  edit its own authorization.

**Illustrated but not production-grade:**

- Personas are Snowflake roles granted to one operator, switched manually. In
  production the principal is an end user, and the mapping comes from the
  application's own permission system.
- The entitlement table is populated by a deploy script. In production it is
  synchronised from the system of record.

## Identity: the gap that matters

The demo keys the policy on `CURRENT_ROLE()` first and `CURRENT_USER()` second.
Both work, and the `CURRENT_USER()` path is the one that matters, because it is
how production should behave: the policy resolves the actual human asking.

CoWork passes real end-user identity, which is why this demo uses CoWork rather
than a persona dropdown in a custom application. A dropdown would prove nothing
about enforcement, because the backend would still be one identity choosing what
to claim.

What production still needs:

1. **Identity mapping.** The application's permission records need to land in
   `ENTITLEMENT` keyed on the Snowflake identity of the end user, refreshed on a
   defined cadence with a defined staleness tolerance. Revocation is the case to
   design for: a removed permission must stop returning rows, and the acceptable
   lag needs to be an explicit decision rather than an accident of the sync
   schedule.
2. **No shared service identity.** If an embedding application calls the agent
   with one service account, every user inherits that account's scope and every
   guarantee here is void. A service identity does not carry end-user permissions.
   This has to be solved with delegated identity, not with a filter the backend
   remembers to add — a filter the application controls is a filter the
   application can forget.
3. **Thread and cache scoping.** Conversation history and any result cache are
   additional copies of the data and need the same scoping as the tables. Not
   addressed here, and not tested.
4. **Audit.** Who asked what, under which entitlements, and what came back.

## Backstage embedding

No Backstage user interface is built. CoWork is the chat surface for this demo,
which was a deliberate choice: it supplies real end-user identity, so the
governance claim is demonstrated rather than asserted.

What the demo does establish about the embed path is the contract. The agent is a
first-class Snowflake object and is callable from an application over the Cortex
Agent REST endpoint, with the caller's identity determining scope. An embedded
Backstage chat panel would call that endpoint and render the response.

What it does not establish is anything about Backstage itself: no user interface,
no authentication flow, no session handling, and no assessment of how a chat panel
would fit existing workflows. Treat the architecture diagram as the intended
shape, not as a completed integration.

## Data

All data is synthetic and deterministic, generated by `HASH()` against a pinned
`DEMO_AS_OF`. Every label, artist, and recording is fictional. No customer data,
no customer account identifiers, and no production schema is referenced anywhere
in this repository.

The streaming-service names in `DIM_DSP_SERVICE` — Spotify, Apple Music, YouTube,
Amazon — are the one exception to "everything is invented," and only as names.
They are used descriptively so the royalty reporting problem stays legible. Every
revenue figure, stream count, and reporting gap attributed to them is synthetic,
including the seven-day outage described below. Those names are the trademarks of
their respective owners, and this project is not affiliated with, endorsed by, or
sponsored by any of them. If you fork this for a public-facing purpose and would
rather not carry the association, `DIM_DSP_SERVICE` is a single seven-row
`VALUES` block in `sql/02_data.sql`; renaming it invalidates the pinned figures in
`docs/EXPECTED_RESULTS.md` and the value spot checks in `tools/run_tests.sh`,
which must be regenerated.

The two fact tables are deliberately **not** reconciled to each other. They stand
in for two different source systems: monthly royalty statements and daily DSP
activity. Streams multiplied by any rate will not equal revenue. That is realistic
and it is also why the two grains must never be joined.

The synthetic data was shaped to make specific behaviors demonstrable — a
three-way title collision, a seven-day DSP outage inside the August window, a
two-way tie at the streaming peak, incomplete trailing days, an unreleased
statement month. Real data will not be this cooperative, and the checks in the
semantic views matter more there, not less.

## Deliberately out of scope

Shopify ingestion and write-back, activation tooling, email support automation,
contract extraction, royalty-payment calculation, forecasting, DSP per-plan rate
estimates, and scheduled report delivery. Also excluded by design: retrieval and
search tools, predictive models, and any orchestration framework beyond the single
agent.

## Claims not made

No ROI figure, no productivity multiplier, and no performance benchmark. Latency
in `docs/TEST_EVIDENCE.md` is a set of single measured observations on an XSMALL
warehouse with one sequential caller, recorded so the numbers are honest rather
than to characterise performance.

Verified queries improve accuracy on the phrasings they cover. They do not
guarantee correctness for a reworded question, and four genuine defects were found
and fixed during verification that each looked entirely plausible until checked
against an independent reference. That is the argument for keeping the reference
queries: not that the agent is untrustworthy, but that trust has to be
re-establishable on demand.
